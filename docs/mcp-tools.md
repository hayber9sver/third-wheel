# MCP tools

The AI talks to the running app through the MCP server `packages/mcp-server`, which uses the
app bridge below. The app must be running; otherwise every tool answers "Third Wheel is not running".

## Setup (Claude Code)

1. `pnpm install && pnpm build:mcp` → one runnable file `packages/mcp-server/build/third-wheel-mcp.js`
   (`pnpm build` builds it too). Node 22+.
2. Put this in your CAD project's `.mcp.json`, with the **absolute** path to your clone:

   ```jsonc
   {
     "mcpServers": {
       "third-wheel": {
         "command": "node",
         "args": ["/abs/path/third-wheel/packages/mcp-server/build/third-wheel-mcp.js"],
       },
     },
   }
   ```

3. Start the app (`pnpm dev`), then Claude Code in the project folder; `/mcp` shows `third-wheel`.

The app shows the same setup with the real path: click the AI status in the status bar (or "Connect an AI agent…" on
the start view) for a copyable `claude mcp add third-wheel -- node "<path>"` (optionally `--scope user`) and `.mcp.json`
snippet. Packaged builds look for the server at `<resources>/mcp/third-wheel-mcp.js` (the installers ship it).

## Tools

All answers are compact JSON text, except `render_region` (a PNG + JSON text). Lengths mm, areas mm².
Errors come back as tool errors with a readable message (`isError`).

**modelId** = first 12 hex digits of the file's sha256 (`modelIdOf` in core). Every new STEP export
gets a new id. Tools that take one fail with "call load_model" when the app shows a different model —
except `get_annotations`, which also reads a model opened earlier in the same app window.

### Review payload (`get_annotations`)

Built by geometry `review.ts`; typically < 1k tokens (a 130-body assembly, 2 markers: ~860).
Positions to 0.01 mm, directions to 1e-3, areas to 0.1 mm².

- `model` file name, `path` (its full path on this computer, so you can edit the file or write the next
  version beside it; added by the app), `units: "mm"`.
- `comments[]`: `id`, `text`, `status`, `by` (`human` / `ai`), `markers` (marker ids; empty = about the
  whole model), `linkedModels?` (other model file names the comment is about), `replies?` (the
  thread, oldest first, the last 10: `by`, `text`, `status?` = what the comment was set to with that
  reply; an older `note` comes first as an AI reply) + `moreReplies?` (earlier ones left out).
- `markers[]` (only those the listed comments point at, first-mention order): `id`, `name`,
  - `paint?`: `area`, `centre` (area-weighted), `size` (bbox), `normal` (mean, unit), `flatness` (1 flat …
    0 facing all ways), `patchCount`, `patches?` (largest ≤ 5: `area`, `centre`) + `morePatches?`,
    `faces[]` (CAD faces under the paint, most painted first, ≤ 8; entity fields + `covered` 0–1) + `moreFaces?`.
  - `entities?` (held B-rep entities, ≤ 10) + `moreEntities?`.
- Entity fields (only those that apply): `kind` (`vertex` / `edge` / `face` / `body`), `id` (traversal
  index), `body` (index → name in `bodies`), `type` (`plane`, `cylinder`, `line`, `circle`, …), `form`,
  `radius`, `minorRadius`, `length`, `arcAngle` (partial arcs only), `halfAngle`, `area`, `point`
  (vertex / centre / apex / a point on the plane or axis), `dir` (normal / direction / axis), body `size` + `faces`.
- `bodies`: `{ "<body index>": "<name>" }` for every body mentioned.

### Part requests

A comment may carry `parts[]`: library parts (bd_warehouse) the user chose in the Library panel. Each:
`id` (`p1`, …), `source` (`kind: "library"`, `library`, `version?`, `cls`, `params` = the standard type, size
or numbers the user fixed; a missing one is yours to choose, e.g. the size from the hole it goes in;
`simple: false` = a real thread was asked for, `simple: true` = none; bd_warehouse screws and nuts default to no
thread, so a missing `simple` gives smooth screws),
`copies`, `scope` (`"whole"` or `{ subparts: [names] }`), `target?` (`markerIds`, `mode?`: `each` or
`pattern`), `note?` (a special requirement), `result?` (yours, below). The comment's `text` is the
instruction. Build the parts with build123d / bd_warehouse, place them at the target markers, export a new
model file and `load_model` it with `revisionOf`. Report with `partResults` on `set_comment_status` or
`reply_to_comment`: one entry per part, `{ partId, status, bodies?, note? }` with `status` `placed`,
`skipped`, `failed` or `needs-info` (put the question in `note` or the reply). The app stores each as the
part's `result` and shows it on the comment. An unknown `partId` is an error and nothing is changed. The
answer has `partsUpdated`.

Step-by-step recipes (start of a session, keeping names, placing a library part at a hole, cutting a pocket, reporting) are in `docs/recipes.md`.

### Keeping the user's body names

The Bodies list shows the names inside the STEP file. build123d's `import_step`, the results of boolean
operations and `export_step` drop them: the new file then has bodies called `SOLID` / `COMPOUND` (or
codes like `=>[0:1:1:2]`) and no assembly nesting, and the user cannot find their parts. When you change a
model with build123d, set `.label` on every solid you export (the text of the previous version's
`PRODUCT` names) and keep the nesting with `Compound(label=…, children=[…])`. When `load_model` is given a
`revisionOf` and most of the previous version's custom names are missing in the new file, the result has
`namesLost` with this advice; fix the names, export under a new file name and load it again.

### Picture facts (`render_region`)

- `view` (one picture) or each of `tiles[]`: `viewDir` (unit, from the region towards the camera; the
  camera looks along −viewDir), `up` (world direction that is up in the picture), `center` (world point
  at the picture centre, mm), `mmPerPx` (orthographic), `ghosted[]` (`body`, `name`: parts in front of
  the region drawn faint and see-through).
- Tiles also have `number` (label top-left, none with one tile), `group` (index into `groups`),
  `markerIds`, pixel rect `x`, `y`, `size`. `skipped`: group indices with nothing to draw.
- Asked markers in their own colours, the rest grey with dark edges on white.

## App bridge (MCP server ↔ running app)

- The app opens a WebSocket on `127.0.0.1` (random free port) at start, unless `THIRD_WHEEL_BRIDGE=0`.
- It writes a **bridge file**: `{ app, protocol, port, token, pid, version }`, file mode 0600, new random
  token each start, removed on quit (only if a later app copy hasn't taken it over; the last started copy wins).
  - macOS `~/Library/Application Support/third-wheel/bridge.json`
  - Windows `%APPDATA%\third-wheel\bridge.json`
  - `THIRD_WHEEL_BRIDGE_FILE=<path>` overrides it in both the app and the client (e2e tests use their own).
- Clients connect with `Authorization: Bearer <token>`. Refused before the WebSocket opens: wrong / missing
  token (401), any `Origin` header (= a web page, 403), a `Host` other than `127.0.0.1:<port>` / `localhost:<port>` (403).
- Messages are JSON. Request `{ id, method, params? }` (≤ 1 MB) → `{ id, result }` or
  `{ id, error: { code, message } }`. Codes: `bad_request`, `unknown_method`, `no_window`, `timeout`, `failed`.
  Requests may overlap; answers match by `id`.
- Client-side errors (`BridgeError.code`): `not_running` (no file, or nobody listening — a crashed app's file),
  `unauthorized`, `refused`, `version_mismatch`, `closed`, `timeout`, `connect_failed`.

| Method                                                                                 | Answered by   | Result                                                         |
| -------------------------------------------------------------------------------------- | ------------- | -------------------------------------------------------------- |
| `ping`                                                                                 | main          | `{ app: 'third-wheel', version, protocol }`                    |
| `status`                                                                               | window        | `{ model: { path, name, contentHash, modelId } \| null }`      |
| `load`, `annotations`, `request_review`, `wait_review`, `render`, `set_comment_status` | main + window | see tools above (params / results in core `bridge-methods.ts`) |

Code: protocol `packages/core/src/bridge.ts`; server `apps/desktop/src/main/bridge.ts` (handlers in
`main/index.ts`, window methods via `askWindow` → renderer `onBridgeRequest` in `main.ts`); client
`packages/mcp-server/src/bridge-client.ts` (`connectBridge`, `call`). Tools: `packages/mcp-server/src/tools.ts`
(one bridge connection per tool call), entry `cli.ts`. Time limits: window answers 30 s; `load` 10 min,
`render` 2 min, `wait_review` its own timeout + 10 s (client + 20 s).
